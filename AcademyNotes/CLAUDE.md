# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**AcademyNotes — Academic Tracking Prototype v0.1**: a Flask + vanilla-JS
academic *tracking* platform (Spanish UI), not just a gradebook. Four roles —
`admin`, `teacher`, `student`, `family` — each with its own blueprint and
dashboard. Data lives in SQLite at `instance/academynotes.db`, generated by
`seed.py` and **not** committed.

It is deliberately a **research prototype**: the publication policy, alert
thresholds, period count and recovery rules are hypotheses to validate with
real users, not settled requirements. Don't harden them into the schema or the
code without being asked. `README.md` states this contract to users; keep it
true.

## Architecture

**Three layers, strictly:** blueprint route → `services/*.py` → `core/db.py` →
SQLite. Routes never write SQL; services never read `request` or `session`
(they take the acting `user` dict as a parameter). `core/db.py` is the only
module importing `sqlite3`.

`core/db.py` gives `query_all` / `query_one` / `scalar` / `execute` (commits,
returns lastrowid) / `transaction()` (context manager; used for Excel import so
a failure leaves nothing applied) / `init_db()` (drops and recreates from
`core/schema.sql`). One connection per request via `flask.g`.

**Authorization is per resource, not just per role.** `role_required(...)`
gates the role; `services/authorization.py` then proves the resource belongs to
the caller — `assert_assignment_owner`, `assert_activity_owner`,
`assert_grade_owner`, `assert_can_view_student`. Any new teacher route that
touches an assignment/activity/grade must call the matching assert; admins pass
all of them by design. Violations raise `PermissionError_` (defined in
`core/security.py`), which `app.py` turns into 403 HTML or JSON.

Passwords use `werkzeug.security`; `SECRET_KEY` comes from
`ACADEMYNOTES_SECRET_KEY` or a generated `instance/dev_secret_key`. Never
reintroduce a literal key or a plaintext password.

## The two ideas that drive the data model

**1. A grade hangs off an activity.** `activities` (name, kind, `weight`,
period, due date) → `grades` (one row per student per activity, `UNIQUE`).
Averages are **weighted**: `grade_service.weighted_average()` computes
`Σ(score×weight)/Σ(weight)` over graded rows only. Never use `AVG()` for a
student average — a test asserts the difference.

**2. Registering is not publishing.** `grades.status` is
`borrador → publicada → final`. Visibility for students and families is
`grade_service.visibility_condition()` / `_is_visible()`:

- `reporte_activo` **off** (default): visible only if `published` *and*
  `published_report_id` points to a `reports` row with status `publicado`.
- `reporte_activo` **on**: any `publicada`/`final` grade is visible.

The toggle lives in `settings` (admin → Ajustes) and is meant to be flipped
during demos. When a grade is not visible, `student_scores()` masks `score`,
`status` **and `id`** — the id is nulled so a student cannot request review of
an unpublished grade. The activity itself always stays visible: students must
see what work exists even when the mark is not out.

Other model notes: `teaching_assignments` (teacher × subject × group × year) is
the authorization unit; a year may have 3 **or** 4 `academic_periods` — never
assume four; `students.student_code` is the stable identifier Excel import
matches on (never names).

## Conventions

- UI strings, flash messages, JSON `message` values and route URLs are
  **Spanish** (`/profesor`, `/estudiante`, `/familia`, `/admin`, `/entrar`).
  Code, identifiers and docstrings are **English**. Source files avoid accents
  and `ñ` in Python/JS comments; templates use HTML entities where needed.
- JSON endpoints return `{"ok": True, ...}` or `{"ok": False, "message": "..."}`
  with 400 (validation), 401 (no session), 403 (wrong role or resource).
  Services raise `ValidationError` (defined per service) and routes translate.
- Every write that a user could later dispute goes through
  `audit_service.log(user, action, entity, entity_id, description, old, new)`.
  Grade changes must record old → new; the teacher's confidence in the system
  is the point.
- Frontend: server-rendered Jinja + small ES modules in `static/js/`
  (`ui.js` holds `postJson`/`openModal`/`status`). Fetch calls use
  **relative** URLs — no hardcoded host or port, no CORS. When building HTML
  strings, pass user data through `escapeHtml`.
- Alerts (`alert_service.py`) are pure functions with no DB access, so
  `grade_service` can import them without a cycle. Keep them explainable: every
  state ships the `motivos` that produced it, and the wording avoids alarm
  ("requiere atención", never "estás perdiendo").
- The feedback "suggestion" is rule-based simulation. There is no AI, and it
  must never set a score.

## Deployment

Live at <https://academynotes-demo-production.up.railway.app> — Railway project
`AcademyNotes`, service `academynotes-demo`, built from the `Dockerfile` with
root directory `AcademyNotes`.

**Auto-deploy on push is NOT active yet.** The service was created through the
API and has no GitHub deployment trigger, so pushing to `main` does not rebuild
anything; the user has to connect the repo once in the Railway dashboard
(service → Settings → Source). Until that is done, do not tell the user a push
reached the live demo — verify with `list-deployments` before claiming it.

The demo database is baked into the image at build time (`RUN python seed.py`),
so every deploy resets the data to a clean, reproducible demo. Don't add a
volume without being asked — the reset is the intended behaviour.

## Publishing changes (standing instruction from the user)

Push to `main` continuously — small, frequent commits rather than one big drop
at the end. `main` is what the deployment tracks, so it must always hold the
latest work.

Before pushing, decide whether the change **compromises the software**: tests
fail, a migration/reset of the demo DB is required, the schema changes, or a
whole subsystem is replaced. Ambiguous cases count as compromising.

- **Safe change** (`python -m pytest tests -q` passes, no schema or data
  reset): commit and push straight to `main`.
- **Compromising change**: first snapshot the *current* `main` onto a backup
  branch — `git branch respaldo/<fecha>-<motivo> origin/main` and push it —
  then push the new work to `main`. The backup keeps the last known-good state
  recoverable; `main` still moves forward.

Never leave the new work only in a local commit: unpushed work is invisible to
the deployment and to the user.

## Testing

`tests/conftest.py` builds a minimal school (1 teacher + 1 assignment, a second
teacher and group for negative permission cases, 2 students, 1 guardian) on a
per-test temp DB. `tests/` covers auth, per-resource permissions, weighted
averages, the publication flow with the `reporte_activo` toggle, Excel
round-trip and rollback, and review + audit. Add a test alongside any change to
publication visibility, weighting or authorization.
